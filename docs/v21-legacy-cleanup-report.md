## 3. Findings (full inventory)

### 3.1 `dist/` is tracked by git — `SAFE_REMOVE`

| Field | Value |
| --- | --- |
| Path | `dist/**` |
| Count | 1,479 files in git, 1,731 in working tree |
| `.gitignore` entry | **Missing** |
| Verification | `git ls-files dist/ \| wc -l` returns 1479 |

**Why it's a problem:**

- Every TypeScript build dirties hundreds of `dist/*.js` and
  `dist/*.d.ts` files.
- Git status shows ~1500 "modified" files after every local build.
- PRs include unrelated `dist/` churn that hides the real diff.
- Production builds should regenerate `dist/` from `src/`, never
  read it from git.

**Recommended action:**

1. Add `dist/` to `.gitignore`.
2. Remove from git index: `git rm -r --cached dist/`
3. Commit: `chore: untrack dist/ build output`
4. Document in CONTRIBUTING that production deploys build from
   `src/` and serve from a fresh `dist/`.

**Rollback:** `git revert <commit>` restores tracking. (Builds
continue to work either way.)

### 3.3 Deprecated DTO fields kept for client compatibility — `LEGACY_QUARANTINED`

| Field | Files | Used by clients? |
| --- | --- | --- |
| `effectiveDebtKd` | 6 backend DTOs + 4 web type definitions | Yes — old mobile / integration clients still read it |
| `cashTodayKd` (always `null`) | `src/driver-oversight/driver-oversight.service.ts` | Possibly — kept as `null` placeholder for stale UIs |
| `heldCashKd` (always `null`) | Same | Same |
| `getEffectiveDebtKdBreakdown` | `src/orders/orders.service.ts` | Possibly |
| `getOperationalDebtKdBreakdown` (the canonical replacement) | `src/orders/orders.service.ts` | Yes |
| `ORDER_SERIAL_KEY` (legacy serial counter) | `src/serials/serial-counter.service.ts` | No — kept "for old DBs" only |

**Why they exist:**

- `effectiveDebtKd` is the V20.3 name for what is now
  `operationalDebtKd`. The DTO carries both fields so older
  clients (mobile, third-party integrations, CSV exports) keep
  working without coordinated redeploy.
- `cashTodayKd` / `heldCashKd` were V20.6 SSoT-locked to `null` —
  driver cash now comes only from
  `GET /api/cash-intelligence/dashboard`. The fields are kept as
  `null` placeholders so old UIs don't crash on missing-property.

**Recommended action:**

1. Audit production telemetry / API logs to confirm no client
   reads `effectiveDebtKd` exclusively (i.e. without also reading
   `operationalDebtKd`).
2. If telemetry confirms zero exclusive reads, schedule removal
   in V22 with a clear deprecation window in the API changelog.
3. If telemetry shows reads, keep them; revisit in V23.

The same procedure applies to `cashTodayKd` / `heldCashKd`.

`ORDER_SERIAL_KEY` is a backend constant that no live code path
references. Recommended: SAFE_REMOVE in V22.

**Rollback:** trivial — `git revert` of the removal restores the
field. Old clients would be insulated by the `?` optional marker
(no backend behaviour change).

3. Update `web/src/App.tsx` route mounts.
4. Verify all guards still apply (`RequireAccess`, `RequireRole`).
5. Verify the page still renders + financial guards pass.

**Rollback:** trivial per-page — `git revert` of the move PR.

## 6. Verification protocol (must pass for every cleanup PR)

Per V20.8 charter (proven safe across 24 file deletions):

For each file removed:

1. ✅ `Grep` for the exported symbol returned **zero** external
   consumers across `web/src/` and `src/`.
2. ✅ `Grep` for the file path / dynamic `import()` returned
   **zero** matches.
3. ✅ Static call-graph confirmed orphan.
4. ✅ Full backend test suite (`npx jest`) passed BEFORE delete.
5. ✅ Full frontend test suite (`npm --prefix web test`) passed BEFORE delete.
6. ✅ Backend build (`npx nest build`) succeeded BEFORE delete.
7. ✅ Frontend build (`npm --prefix web run build`) succeeded BEFORE delete.
8. ✅ V21 banking guards (`npx jest src/finance/v21-canonical-banking-guards.spec.ts --runInBand`) passed BEFORE delete.
9. ✅ Same for AFTER delete (steps 4–8 repeated).
10. ✅ Reconciliation against staging passed AFTER delete (manual check).

Per V20.8 charter: any failure on (4)–(10) stops the phase.

## 7. Rollback policy

Every cleanup commit is git-traceable. To revert any single file:

```bash
git checkout HEAD~ -- <path>
```

To revert a whole phase:

```bash
git revert <commit-sha>
```

The append-only DB triggers protect financial data regardless of
code changes — even a malicious cleanup cannot mutate history.
