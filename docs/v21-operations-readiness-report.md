## 2. What is in place

### 2.1 Structured logging

`src/observability/`, `src/main.ts`, and Nest's `Logger`:

- Every log line carries a `[TAG]` prefix:
  - `[FINANCIAL_DOMAIN_EVENT]`
  - `[FINANCIAL_SNAPSHOT_REFRESH]`
  - `[FINANCIAL_PERIOD_VIOLATION]`
  - `[RECONCILIATION_DRIFT]`
  - `[UI_CONSISTENCY_MISMATCH]`
  - `[FINANCIAL_REALTIME_GATEWAY]`
  - `[CASH_HANDOVER_TRANSFER]`
  - `[INVOICE_AUDIT]`
  - `[ORDER_STATE_TRANSITION]`
  - `[PAYMENT_GATEWAY_FAILURE]`
- Every request has:
  - `requestId` (via `requestIdMiddleware`)
  - `correlationId` (via `requestContextMiddleware` + AsyncLocalStorage)
- Logs are JSON-on-stdout (Loki-scrape-ready).

**Action:** None — the structured-logging foundation is in place.

### 2.4 Error reporting — Sentry

Documented in [`OBSERVABILITY.md` §3](./OBSERVABILITY.md#3-error-reporting--sentry):

- Backend reports unhandled exceptions to Sentry when `SENTRY_DSN` is set.
- Frontend reports React + `window.onerror` + unhandled promise rejections.
- Validation / 404 errors are suppressed (Sentry inbox stays

- DB connection strings, JWT tokens, request bodies > 1 KB are

## 3. Gaps (what to add)

### 3.1 Grafana dashboards-as-code

**Gap:** Dashboards are operator-deployed; nothing in this repo
provisions them.

**Recommendation:** Add `ops/grafana/` directory with JSON
dashboard manifests under git versioning:

- `payments-dashboard.json` — payment finalize latency / success / failure / SLO burn.
- `cash-monitor-dashboard.json` — cash classifier / handover / verification rates.
- `reconciliation-dashboard.json` — drift over time, identity-by-identity.
- `realtime-dashboard.json` — WS subscriber count, broadcast rate.
- `queue-dashboard.json` — per-queue depth, retry, DLQ, latency.
- `db-dashboard.json` — Postgres connections, slow queries, top
  endpoints by latency.
- `system-dashboard.json` — node memory / CPU / HTTP latency.

**Risk:** LOW (operator-side; not application code).

**Effort:** ~ 8 hours per dashboard.

### 3.2 Prometheus alerting rules

**Gap:** Alerts today are Discord webhook calls from
application code. Prometheus alert rules (Alertmanager-driven)
would be more reliable and reduce noise.

**Recommendation:** Add `ops/prometheus/alerts.yml`:

```yaml
groups:
  - name: payments
    rules:
      - alert: HighPaymentFailureRate
        expr: rate(payments_finalize_failure_total[5m]) > 0.05
        for: 5m
        labels: { severity: page }
        annotations:
          summary: "Payment finalize failure rate > 5% for 5 minutes"
          runbook: "https://wiki/runbooks/payment-failure"

      - alert: PaymentSLOBurn
        expr: slo_payment_error_budget_remaining_ratio < 0.5
        for: 10m
        labels: { severity: warn }
        annotations:
          summary: "Payment SLO error budget < 50%"

  - name: queues
    rules:
      - alert: QueueBacklogSpike
        expr: queue_jobs_waiting > 1000
        for: 5m
        labels: { severity: page }

      - alert: QueueDelaySLO
        expr: slo_queue_delay_estimate_s > 300
        for: 5m
        labels: { severity: warn }

  - name: reconciliation
    rules:
      - alert: ReconciliationDrift
        expr: increase(reconciliation_drift_total[1h]) > 0
        for: 0m
        labels: { severity: page }
        annotations:
          summary: "Reconciliation drift detected"
          runbook: "https://wiki/runbooks/reconciliation-drift"

  - name: gateway
    rules:
      - alert: GatewayCircuitOpen
        expr: circuit_state > 0
        for: 1m
        labels: { severity: warn }
```

**Risk:** LOW.

**Effort:** ~ 4 hours.

### 3.3 Sentry release tracking

**Gap:** `SENTRY_RELEASE` env can be unset; without it, source maps
do not tie to releases.

**Recommendation:** Make `SENTRY_RELEASE` part of the deploy script:

```bash
SENTRY_RELEASE=$(git rev-parse --short HEAD)
kubectl -n production set env deploy/safari-erp SENTRY_RELEASE=$SENTRY_RELEASE
```

**Risk:** LOW.

**Effort:** ~ 1 hour.

### 3.4 OpenTelemetry tracing

**Gap:** OTel SDK is documented but not yet wired
(see [`architecture/V20.4_ARCHITECTURE.md` Phase 7](./architecture/V20.4_ARCHITECTURE.md#phase-7--observability-stack--%EF%B8%8F-infrastructure-decision-record)).

**Recommendation:** Wire `@opentelemetry/sdk-node` in `main.ts`,
opt-in via `OTEL_EXPORTER_OTLP_ENDPOINT` env. Minimal code change;
big payoff for distributed tracing.

**Risk:** LOW (opt-in; absent OTEL endpoint = no-op).

**Effort:** ~ 8 hours including instrumenting hot paths.

### 3.5 PITR (Point-in-Time Recovery) automation

**Gap:** PITR is documented in
[`architecture/operational-runbooks/backup-restore.md`](./architecture/operational-runbooks/backup-restore.md)
but the WAL archive is not automated in this repo.

**Recommendation:** Document the cloud-provider PITR setup
(`max_wal_size`, `archive_command`) in BACKUP.md and add a CI job
that verifies the archive is reachable.

**Risk:** LOW.

**Effort:** ~ 4 hours.

### 3.6 Restore drill automation

**Gap:** The drill is on a per-quarter calendar — relies on
discipline.

**Recommendation:** Add a staging cron that:

1. Spins up a fresh staging-restore DB.
2. Pulls the latest production backup from S3.
3. Restores it.
4. Runs reconciliation.
5. Posts the result to `#ops`.

**Risk:** LOW (runs in staging).

**Effort:** ~ 8 hours.

### 3.7 Per-flow latency SLO

**Gap:** SLOs exist for payment finalize, but not for handover,
custody verify, snapshot refresh, or reconciliation runs.

**Recommendation:** Add SLO gauges for the top operational flows:

- `slo_handover_success_ratio` (target 99.9% in 1m)
- `slo_custody_verify_success_ratio`
- `slo_snapshot_refresh_lag_ms` (P95 target < 1s)
- `slo_reconciliation_run_success_ratio` (target 100%)

**Risk:** LOW.

**Effort:** ~ 4 hours per SLO.

### 3.8 Customer-facing payment status SSE

**Gap:** Customer-facing payment status polls
`/api/payments/status/:orderId`. SSE would give them sub-second
updates.

**Recommendation:** Reuse the existing realtime gateway to push
payment status to a customer's connection (already partially done
for the operational dashboard; extend to public).

**Risk:** MEDIUM (needs auth scoping for the public side).

**Effort:** ~ 16 hours.

## 7. PITR strategy

Documented in [`architecture/operational-runbooks/backup-restore.md` §5](./architecture/operational-runbooks/backup-restore.md#5-production-restore-pitr--point-in-time).

Cloud-provider native (RDS / Cloud SQL / AlloyDB):

```bash
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier safari-erp-prod \
  --target-db-instance-identifier safari-erp-restore-<timestamp> \
  --restore-time <iso8601>
```

After restore:

1. Dump affected tables only.
2. Re-insert via forward-fix script (always reversal entries —
   never `UPDATE` financial rows).
3. Run reconciliation.
4. Lift any READ_ONLY flag.
