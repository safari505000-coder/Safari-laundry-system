### 2.3 Verdict

The user's target structure (10 top-level modules) is **conceptual**:
it represents the financial core. The actual backend has **60
top-level modules** because the system covers ERP functionality
(payroll, attendance, expenses, leaves, inventory, …) that lives
**outside** the financial core but is needed for operations.

**Recommendation: keep the current 60-module layout.** Flattening
under the target's 10 buckets would:

- Force unrelated domains into one folder (`payroll/` under
  `finance/` mixes compensation with the canonical ledger).
- Break the existing barrel exports.
- Force a cascade of import-path updates across every file.
- Provide no operational benefit.

The relevant **target modules are all present** under
`src/finance/`:

- ✅ `finance/` — canonical projections, snapshot, replay, hash, immutable, services.
- ✅ `finance/collections/` — collections workflow.
- ✅ `finance/risk/` — risk scoring.
- ✅ `finance/fraud/` — fraud detection.
- ✅ `finance/reconciliation/` — reconciliation pipeline.
- ✅ `finance/snapshots/` — snapshot service (V20.4 Phase 1).
- ✅ `customers/` — customer master.
- ✅ `subscribers/` + `subscriptions/` + `subscription-plans/` — three modules forming the subscription domain.
- ✅ `accounting/` — accountant-facing operations.
- ✅ `domain-events/` + `safari-stream/` — realtime / event bus.
- ✅ `common/` — the shared/ equivalent.

**Action:** Document this in `architecture/module-ownership.md`
(already done in §1). No physical reorganisation required.

## 4. Circular dependency report

### 4.1 Backend (`madge --circular --extensions ts ./src`)

**8 cycles found** — all between `orders`, `customer-ledger`,
`payments`, `finance/outstanding`, `auth/auth.module`, and
`finance/finance.module`. All are resolved via NestJS
`forwardRef()` per the recommended pattern:

```
1) common/services/payments.service.ts
   > customer-ledger/customer-ledger.service.ts
   > orders/orders.service.ts

2) customer-ledger/customer-ledger.service.ts
   > orders/orders.service.ts

3) orders/orders.service.ts
   > finance/outstanding/outstanding.service.ts

4) auth/auth.module.ts
   > finance/finance.module.ts
   > payments/payments.module.ts
   > customer-ledger/customer-ledger.module.ts
   > orders/orders.module.ts

5) customer-ledger/customer-ledger.module.ts
   > orders/orders.module.ts

6) orders/orders.module.ts
   > finance/outstanding/outstanding.module.ts

7) payments/payments.module.ts
   > customer-ledger/customer-ledger.module.ts
   > orders/orders.module.ts

8) auth/auth.module.ts
   > finance/finance.module.ts
   > payments/payments.module.ts
   > customer-ledger/customer-ledger.module.ts
   > orders/orders.module.ts
   > serials/serials.module.ts
```

### 4.2 Why these cycles exist

The settlement triangle is **inherently bidirectional**:

```
OrdersService (state machine, holds Order entity)
   needs → CustomerLedgerService (settlement orchestrator)
   needs ← OrdersService (to query order status, line items)

PaymentsService (gateway integration)
   needs → CustomerLedgerService (delegate settlement)
   needs ← OrdersService (to claim the order via conditional update)

OutstandingService (reads outstanding orders)
   needs → OrdersService (the source data)
   needs ← OrdersService (some intake paths check outstanding before insert)
```

Resolving these "structurally" would require splitting `OrdersService`
into a state-machine service and a query service — a multi-month
refactor with risk to a critical write path.

### 4.3 Mitigation in place

- All cycles are explicitly resolved via `forwardRef()` in module
  declarations (verified in
  `src/orders/orders.module.ts:20-27`).
- The cycles are **module-level**, not symbol-level — at runtime
  Nest constructs the services lazily so no actual import-time
  loop occurs.
- Tests exercise the boundary.
- Build succeeds.

### 4.4 Frontend (`madge --circular --extensions ts,tsx ./web/src`)

```
✅ No circular dependency found.
```

The V20.7 + V20.8 frontend rebuild eliminated all UI-side cycles.

### 4.5 Recommended action

| Cycle | Action |
| --- | --- |
| 1, 2, 5, 7 (orders ↔ customer-ledger ↔ payments) | **Leave as-is** — `forwardRef()` is the canonical NestJS solution; refactoring risk outweighs benefit. |
| 3, 6 (orders ↔ outstanding) | Document as known cycle; `forwardRef()` already in place. |
| 4, 8 (auth ↔ finance ↔ payments ↔ customer-ledger ↔ orders) | This is the auth-needs-roles-needs-finance chain. Already `forwardRef`'d. Document. |

Add an automated CI check that **fails the build if a NEW cycle
is introduced** beyond these 8, using madge:

```bash
# Suggested CI script (proposed)
npx madge --circular --extensions ts ./src --json > /tmp/cycles.json
if [ "$(jq 'length' /tmp/cycles.json)" -gt 8 ]; then
  echo "New circular dependency introduced!"
  exit 1
fi
```

### 6.2 The settlement triangle (the cyclic core)

```
       OrdersService ◄────┐
            │             │
            │ delegates   │ queries
            │ settlement  │ status
            ▼             │
       CustomerLedgerService
            │             ▲
            │ delegates   │ orchestrates
            │ to journal  │ wallet+lock
            ▼             │
       PaymentsService ───┘
            │
            │ verifies
            ▼
       UPayments gateway (external)
```

All three nodes participate in cycles 1, 2, 5, 7. All resolved via
`forwardRef()`. The triangle is the **canonical settlement path**;
de-cycling it would mean rewriting how orders are completed.

### 6.3 The deepest module

`general-ledger/` has **zero outgoing imports to domain modules**
(only `prisma`, `common/`, `audit-logs/`). It is the system's
sink — every other module eventually depends on it for the canonical
journal write.

This is **correct architecture**. The canonical writer must be
the deepest dependency; circular flow into it would mean the
journal depends on its own consumers, which would be wrong.
