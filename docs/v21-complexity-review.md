### 3.3 Splits already planned (V20.4 Phase 11)

From `architecture/V20.4_ARCHITECTURE.md`:

> Phase 11 — File Refactor + Clean Architecture ⏳ In flight
>
> Files over 700 lines are tagged for splits in their owning
> module README. V20.4 splits the read layers into the new
> `src/read-models/` folder and the canonical visibility into
> `src/finance/debt-visibility/`. Subsequent V20.4.x PRs extract:
>

**Status:** The V20.4 read-layer splits **shipped**. The remaining
write-side splits (orders, customer-ledger) **did not ship**
because the call-graph cost was too high relative to the benefit.

2,000+-line write service into 4 × 500-line services would:

- Add 4 new files to read.
- Add 4 new module dependencies.
- Spread the wallet-lock + transaction logic across multiple files
  (harder to reason about safety).
- Provide no operational benefit.

The size is high but **the surface area is documented** in
`architecture/financial-core.md` and the methods are well-named.

### 4.2 The one dangerous case — `payroll-unified-page.tsx`

**File:** `web/src/pages/payroll-unified-page.tsx` (2,086 lines)

**Concerns:**

- Combines 5 distinct concerns: payroll cycle, payroll rosters,
  ad-hoc lines, debt holds, and loans.
- Every state change re-renders the entire page.
- New developers struggle to find code (no clear sub-section
  boundaries).

**Recommendation:** Split into 5 sibling pages or 5 child components,
each owning one concern, composed by a thin parent. This is a
**1-week refactor** and **low risk** because the page is read-mostly
(its mutations all go through API endpoints that already have
backend canonical safety).

**Priority:** MEDIUM. Refactor it when next touched substantively.

## 5. Architectural complexity findings

### 5.1 Settlement triangle (`forwardRef` cycle) — Acceptable

```
OrdersService ⇄ CustomerLedgerService ⇄ PaymentsService
```

8 backend cycles total, all between these three services and
their satellites (`outstanding`, `serials`, `auth`).

**Why acceptable:** NestJS `forwardRef()` is the documented Nest
pattern for this case. The runtime impact is zero (Nest constructs
services lazily). The only cost is reader cognitive load.

**Documented in:**
- `v21-structure-hardening-report.md` §4
- `architecture/module-ownership.md` §1

**Action:** None.

### 5.2 Legacy `GeneralLedgerService` mirror writes — Redundant

The legacy single-entry GL is written alongside every canonical
journal entry. Documented as `MEDIUM` risk in V21 audit
findings #11.

**Status:** Phase 6 candidate for retirement.

**Action:** Track in `v21-legacy-cleanup-report.md` §3.11.

### 5.3 Dual cash classifier services — Acceptable

`src/cash-monitor/` (12 services) AND `src/cash-intelligence/` (1 v2 service).

V21 audit notes both exist; the v2 service is the **SSoT for the
traffic-light** while v1 services provide auxiliary cash-classifier
facets (executive view, risk view, exposure view, audit view).

**Recommendation:** Keep both. The v1 services are stable
satellites; rewriting them would be churn without clear benefit.

### 5.4 `web/src/modules/callcenter/` placeholder — Unnecessary

README-only folder pointing to a never-completed rename.

**Action:** Retire (per `v21-legacy-cleanup-report.md` §3.2).

### 5.5 Three customer-360 surfaces — Acceptable

V20.8 charter explicitly notes:

- `CustomerPortal360Page` (CUSTOMER role, self only)
- `CcCustomer360Page` (CALL_CENTER, any customer)
- `CustomerStatementJournalPage` (ACCOUNTANT, any customer + journal)

**Why acceptable:** Three different role boundaries. Merging
violates security scopes. The **components** are unified (V20.7
Financial UI Kit); the **pages** are not.

**Action:** None.

## 6. Performance review

### 6.1 Backend

| Concern | Status | Mitigation |
| --- | --- | --- |
| Hot read paths | `FinancialSnapshot` materialised; rebuildable from journal | V20.4 |
| Slow queries | `db_query_duration_ms` histogram + per-query slow-log threshold | Live |
| Connection pool | Prisma pool tuning via env (`DATABASE_URL?connection_limit=N`) | Operator-side |
| Index coverage | `JournalLine[accountId]`, `JournalEntry[customerId, createdAt]`, `Order[dueDate]`, `DebtLedgerEntry[customerId, createdAt]`, plus V20.4 snapshot indexes | Live |
| Long-running transactions | `prisma.$transaction({ maxWait, timeout })` tuned to prevent runaway locks | Live |
| Cron job lifecycle | Reconciliation hourly + nightly; KPI cron 5-min; snapshot cron 5-min | Live |

**No backend performance concerns identified beyond the existing
mitigations.**

### 6.2 Frontend

V20.7 + V20.8 frontend performance reports document:

- Lazy-route splitting via `modules/shared/routing/lazy-route.tsx`.
- `WindowedList` virtualisation for long lists (V20.8 Phase 4).
- TanStack Query cache tuned per resource.
- React.memo on expensive selectors.
- Suspense boundaries.

**One concern:** `payroll-unified-page.tsx` (2,086 lines) loads
upfront. Recommend lazy-loading its child concerns when the
refactor lands (§4.2).

### 6.3 Bundle size

V20.8 reduced bundle by ~92 KB pre-gzip via dead-code removal.
The current bundle is split per-route (lazy). No critical-path
bundle exceeds the V20.7 budget.

## 7. Future scaling risks

| Risk | When it bites | Mitigation today | Action when bite |
| --- | --- | --- | --- |
| In-process event bus (`@nestjs/event-emitter`) | Multi-pod deployment with high event throughput | Adapter pattern in `src/domain-events/adapters/` | Swap to Redis Streams / Kafka adapter (1-file change per consumer) |
| Single-tenant Postgres | > 10K customers | Index coverage + snapshot read paths | Add read replica (V20.4 Phase 13 plan) |
| BullMQ queues sharing one Redis | High WhatsApp volume affecting `financial-critical` | V20.4 ADR documents queue isolation plan | Provision separate Redis for `financial-critical` |
| Snapshot rebuild duration | > 100K customers | Per-customer rebuild is parallelisable | Parallelise rebuild via worker pool |
| Frontend bundle size | > 5 MB | Code splitting in place | Tree-shake; consider micro-frontend boundary at module level |
| `web/src/pages/` legacy folder | Slows new developer onboarding | Migration plan documented | Continue per-page migration |

None of these are biting today. All are documented with
explicit "what to do when bite" actions.

## 8. Memory leak risks

Audited:

| Pattern | Status |
| --- | --- |
| Long-lived `setInterval` without cleanup | None found (every `@Interval` is in a Nest service with proper lifecycle) |
| WebSocket subscribers not unsubscribing | `FinancialRealtimeGateway` cleans up on disconnect |
| Event-emitter listeners growing | Bounded — each `@OnEvent` is registered once at module init |
| Unbounded in-memory caches | `MetricsService.finalizeSamples` is bounded (`SAMPLE_CAP = 10_000` + `SAMPLE_MAX_AGE_MS = 5min`) |
| TanStack Query cache | Bounded by `gcTime` defaults |

**No memory leak risks identified.**

## 9. Render-waste audit (frontend)

Audited:

| Pattern | Status |
| --- | --- |
| Component re-render on every parent render | Mitigated by `React.memo` where measurably helpful |
| Long lists without virtualisation | `WindowedList` for > 200 rows (V20.8) |
| Re-fetching on every mount | TanStack Query cache with `staleTime` per resource |
| Provider re-render cascade | Top-level providers stable references |
| Heavy computation on render | `useMemo` for derived data |

**No systemic render waste identified.**

## 10. Cache misuse audit

Audited:

| Pattern | Status |
| --- | --- |
| Stale data shown after mutation | Mitigated via `queryClient.invalidateQueries` in mutation `onSuccess` |
| Cache key collisions | Each query key is namespaced |
| Over-caching | `gcTime` defaults bounded |
| Under-caching | Per-resource `staleTime` set |
| Stale-while-revalidate | Standard TanStack pattern |

**No cache misuse identified.**
