## 4. Duplicated state / fetching findings

From `Grep apiJson|apiFetch|fetch\(` against `web/src/pages/`:

- **35+ legacy pages** still use `apiJson` directly — duplicated
  fetching with no shared cache.
- **0** of the new `modules/finance/` or `modules/collections/`
  surfaces use `apiJson` directly — they all flow through
  `useFinancialQuery` (V20.6 / V20.7).

Plan (Phase 4):

- Keep `apiJson` exposed for legacy pages.
- Wrap any **new** finance fetcher in `useFinancialQuery` so the
  cache deduplicates.
- Forbid `apiJson` inside `modules/finance/` + `modules/collections/`
  via the Phase 5 static guard.

## 5. UI-side financial math

The V20.7 Phase 7 static guard already certifies that
`modules/finance/components/`, `modules/collections/components/`,
and `modules/collections/pages/` contain **zero** client-side KD
arithmetic (`parseFloat(*Kd)`, `*Kd.toFixed`, `*Kd + …`,
`Math.round(*Kd…)`, `Number(*Kd)`, `.reduce(* Kd …)`).

Legacy pages still contain plenty (e.g. `subscribers-page.tsx` had
20 such call-sites at the V20.7 audit). They are **not** broken
because each value happens to come from a server field; the
**risk** is future maintenance. Phase 5 of V20.8 expands the guard
to cover **new** code in `modules/` (broader scope) without
regressing on legacy pages, then Phase 7 migrates legacy pages
during their next maintenance touch.
