## 2. Coding standards

### 2.1 TypeScript

- `strict` mode, no `any` (use `unknown` + narrowing instead).
- Explicit return types on public functions.
- `Prisma.Decimal` for monetary values; never `number` for money.
- Avoid `parseFloat` / `Number()` on monetary strings.
- Functional style preferred for projection / read code; OOP for
  service / state-machine code.

### 2.2 NestJS conventions

- One module per domain (`<domain>.module.ts`).
- Service → Repository → Prisma is the standard layering.
- `@Injectable()` services; `@Controller()` routes; `@Module()` composition.
- Use `forwardRef()` for module cycles when justified
  (already in use across the settlement triangle).
- Public surfaces exported from `<domain>/index.ts` barrel.

### 2.3 Prisma

- All schema changes via `prisma migrate dev` (never edit `schema.prisma` manually then forget the migration).
- Migrations are **forward-only**.
- Append-only DB triggers on every immutable financial table.
- `prisma.$transaction` for every multi-step financial write.
- `lockCustomerWalletForUpdateTx` before any wallet read-then-write.

### 2.4 React / Vite

- Functional components only.
- Hooks for state + data fetching.
- TanStack Query for server state.
- Tailwind for styling; design tokens only.
- Co-locate components with their hooks; barrel-export through
  `<module>/index.ts`.

### 2.5 Naming conventions

- Files: `kebab-case.ts` (Nest convention) for backend.
- Files: `PascalCase.tsx` for React components, `kebab-case.tsx` for pages.
- Constants: `SCREAMING_SNAKE_CASE`.
- Types/interfaces: `PascalCase`.
- Domain events: `noun.past-tense` (e.g. `finance.invoice.issued`).
- `sourceRef`s: `DOMAIN:<id>[:VARIANT]`.

### 2.6 Comments

Per the global instruction: **avoid narrating what the code does**.
Comments should explain **non-obvious intent, trade-offs, or constraints**:

```ts
// ❌ BAD
// Increment the counter
counter++;

// ✅ GOOD
// V20.1 hotfix: safeTakeMinor must be 0 for external payments —
// see customer-ledger.service.ts:484-503 for the bug this prevents.
const safeTakeMinor = shouldUseWallet ? Math.min(balanceMinor, totalMinor) : 0;
```

## 3. Financial safety rules (non-negotiable)

### 3.1 The journal is the truth

- Direct `prisma.journalEntry.create` outside `general-ledger/` is **forbidden**.
- Direct `prisma.journalEntry.update` / `delete` is **forbidden**
  (DB triggers refuse anyway).
- Same for `DebtLedgerEntry`, `CollectionsStageEvent`, `PromiseEvent`,
  `FraudAlert`, `FinancialPeriodViolation`,
  `FinancialEventOutbox`, `FinancialEventDelivery`.

### 3.2 Reversal-only corrections

- Corrections write a contra-entry; **never** edit the original.
- Reversal `sourceRef` carries `:REVERSAL` suffix.

### 3.3 Decimal precision

- Internal: `Prisma.Decimal` (4dp).
- API response: string (4dp).
- Display: 3dp via `web/src/lib/kwd.ts`.
- **No** `parseFloat` / `Number()` on monetary strings in execution paths.

### 3.4 Wallet locks

- Every wallet update path acquires `lockCustomerWalletForUpdateTx`.

### 3.5 Atomic transactions

- Every multi-step financial write uses `prisma.$transaction`.

### 3.6 Idempotency

- Every external trigger maps to a deterministic `sourceRef`.
- P2002 catches treat duplicates as no-ops.
- Conditional `updateMany` claims (e.g. `walletSettledAt: null`)
  ensure single-writer wins.

### 3.7 Period locks

- `PeriodLockGuard.assertWriteAllowed` runs before every journal write.
- Closed-period writes throw + log violation.

### 3.8 Frontend display-only

- No financial math on the client.
- Every monetary display flows through `web/src/lib/kwd.ts`.
- 96 V21 banking guards enforce.

## 7. Migration rules

1. **Migrations are forward-only.** Never write `down()`.
2. **Additive-only by default.** `CREATE TABLE`, `ADD COLUMN` (NULLABLE
   default), `CREATE INDEX` are safe single-step migrations.
3. **Destructive migrations require a two-step deploy:**
   - Step A (release N): add new column, backfill, dual-write,
     dual-read (prefer NEW with fallback to OLD).
   - Wait at least one week (one full reconciliation cycle).
   - Step B (release N+1): remove OLD column, single-read NEW.
4. **Never `DROP COLUMN` on financial tables without a follow-up
   migration that has been reviewed by the architect.**
5. **Append-only DB triggers must be installed in the same
   migration that creates the immutable financial table.** Never a
   follow-up migration.
6. **Renames are two-step:** ADD new column with new name,
   backfill, dual-write, then drop old (per §7.3).
7. **Indexes are non-blocking** (`CREATE INDEX CONCURRENTLY` in
   raw SQL when the table is large; the migration must declare it).
8. **Migration name** = short kebab description with phase prefix,
   e.g. `20260508_v21_phase_6_legacy_gl_retirement`.
9. **Test the migration in staging** with a recent prod backup
   before merging.

## 9. Testing strategy

### 9.1 Test pyramid

| Layer | What | Target coverage |
| --- | --- | --- |
| Unit | Pure functions, projection helpers, formatters | High (90%+) |
| Service | Business logic with Prisma mock | High (80%+) |
| Integration | Full module wiring with real DB (test container) | Medium (60%+) |
| E2E | Critical user journeys (POS, payment, handover, void) | Low (10 critical paths) |
| Guard | V21 banking guards, UI consistency, design system | 100% (every rule has a test) |

### 9.2 Critical paths (E2E required)

1. CASH order completion → journal entry lands.
2. KNET online callback → finalize → journal entry lands.
3. Driver handover → manager bag → accountant verify.
4. Invoice void → reversal entry lands.
5. Subscription expiry → wallet untouched.
6. Reconciliation cron → all four identities pass.
7. Snapshot rebuild → equals journal-derived state.
8. Frontend display: Customer 360 shows correct debt for known customer.

### 9.3 Pre-commit checks

```bash
# Frontend lint + type
npm --prefix web run lint
npm --prefix web run type-check

# Backend lint + type
npx tsc -p tsconfig.build.json --noEmit

# Banking guards
npx jest src/finance/v21-canonical-banking-guards.spec.ts --runInBand

# Quick smoke
npm --prefix web test -- --run --reporter=basic
npx jest --selectProjects unit --silent
```

### 9.4 CI required checks

- Backend full test suite.
- Frontend full test suite.
- Banking guards.
- UI consistency guard.
- Component consolidation tests.
- Madge cycle count ≤ 8 (snapshot).
- Migration drift check.
- Build (backend + frontend).
- Type check (both).

## 12. Critical invariant warnings (in-code)

Every service that holds a critical invariant has an inline doc
comment explaining what is at stake. When you encounter one of
these comments, **stop and re-read the matching invariant in
[`architecture/invariants.md`](./architecture/invariants.md)**:

```ts
/**
 * @critical-invariant 1, 2, 9, 10, 14
 *
 * Sole canonical writer of JournalEntry / JournalLine. Every other
 * service that needs to write journal data MUST go through this
 * method. Direct prisma.journalEntry.create from outside this
 * service is a bypass that breaks every audit guarantee in the
 * system.
 *
 * Idempotency: deterministic sourceRef → unique constraint →
 * findUnique short-circuit on retry.
 *
 * Period-lock: PeriodLockGuard.assertWriteAllowed throws on closed
 * periods (when PERIOD_LOCK_ENFORCE=true).
 *
 * Append-only: DB triggers refuse UPDATE / DELETE / TRUNCATE on
 * JournalEntry, JournalLine.
 *
 * If you find yourself wanting to bypass any of the above for
 * "performance", read docs/architecture/invariants.md and stop.
 */
async appendBalanced(db, input) { … }
```

## 13. Architectural Decision Records (ADRs)

ADRs document the reasoning behind significant architectural
choices. They live alongside the architecture docs.

### ADR-001 — Append-only journal

**Status:** Accepted (V20.0)
**Context:** Need bank-grade financial integrity.
**Decision:** All journal tables are append-only at the DB level.
**Consequences:** No row can ever be edited; corrections via
reversal entries only. Auditor-friendly. Higher storage cost.

### ADR-002 — Reversal-only corrections

**Status:** Accepted (V20.0)
**Context:** Need to support corrections without violating
append-only.
**Decision:** Every correction is a separate balanced reversal
entry with `:REVERSAL` suffix on `sourceRef`.
**Consequences:** History intact; reversal traceable; reads must
sum the journal (cannot just look up "current" state).

### ADR-003 — Deterministic `sourceRef`

**Status:** Accepted (V20.1)
**Context:** Need idempotent retries on payment webhooks.
**Decision:** `sourceRef` is computed deterministically from the
business event id (not gateway id). Unique index enforces
single-write semantics.
**Consequences:** Webhook duplicates land as no-ops. Gateway lies
cannot trick the system into double-posting.

### ADR-004 — Single canonical writer

**Status:** Accepted (V20.3)
**Context:** Multiple services were writing journal entries
independently, leading to drift risk.
**Decision:** `DoubleEntryJournalService.appendBalanced` is the
sole canonical writer. Runtime guard
(`guardJournalDelegate`) blocks all other callers.
**Consequences:** All financial writes funnel through one method;
auditing is single-point.

### ADR-005 — V20.4 read-model layer

**Status:** Accepted (V20.4)
**Context:** Live ledger scans for dashboards were slow at scale.
**Decision:** Materialised `FinancialSnapshot` and
`FinancialKpiSnapshot` rebuildable from journal; refreshed via
event bus + 5-min cron.
**Consequences:** O(1) dashboard reads. Snapshot invariants must
be enforced in code (rebuildable guarantee).

### ADR-006 — V20.7 Financial UI Kit

**Status:** Accepted (V20.7)
**Context:** Per-page money displays were diverging.
**Decision:** Single Financial UI Kit at
`web/src/modules/finance/components/`. Every monetary surface
consumes from it. Static + runtime guard.
**Consequences:** No client-side KD math allowed. UI consistency
enforced.

### ADR-007 — V21 Phase 3 immutable snapshots

**Status:** Accepted (V21 Phase 3)
**Context:** Need bank-grade reproducibility for legal-grade
exports.
**Decision:** Snapshot envelopes carry deterministic
`canonicalHash`. `replayStatementSnapshot(events) ==
storedSnapshot(...)` invariant guaranteed by Phase 3 contract
tests.
**Consequences:** Snapshots can be rendered to PDF six months
later and the hash matches.

### ADR-008 — V21 Phase 4/5 frontend financial purity

**Status:** Accepted (V21 Phases 4 & 5)
**Context:** Some pages had local money formatters / aggregations,
risking drift.
**Decision:** 96 banking guards across 41 surfaces; single
canonical formatter (`web/src/lib/kwd.ts`); backend computes every
sum/total.
**Consequences:** Frontend is genuinely display-only. Build fails
on any new violation.

### ADR-009 — `forwardRef()` for the settlement triangle

**Status:** Accepted (V19.x, ratified V20.0)
**Context:** Orders, customer-ledger, and payments form a natural
cycle (each depends on the other for state).
**Decision:** Resolve via NestJS `forwardRef()` at module
boundaries; do not refactor the cycle.
**Consequences:** 8 backend cycles permanently exist; documented
in [`v21-structure-hardening-report.md`](./v21-structure-hardening-report.md).
Refactor risk outweighs benefit.

### ADR-010 — Forward-only migrations

**Status:** Accepted (V20.0)
**Context:** Migration rollbacks have caused data loss in
prior systems.
**Decision:** No `down()` migrations. Bad migrations get a
forward-fix migration in the next release.
**Consequences:** Lower data-loss risk; requires discipline in
migration authoring + staging soak.

### ADR-011 — Cash classifier rules immutable

**Status:** Accepted (per Cursor rule)
**Context:** Cash classifier (5 KD floor, 24h gate,
compliance-never-topRisk) is the SSoT for the cash traffic-light;
operators have wired alerts and procedures around its outputs.
**Decision:** The classifier rules are **immutable** without
architectural review. Documented in
`.cursor/rules/cash-intelligence-safety.md`.
**Consequences:** Operators trust the rules. Changing them
requires re-training operators.

### ADR-012 — UPayments server-side verification

**Status:** Accepted (V20.0)
**Context:** Client-side return URL can be spoofed.
**Decision:** Every payment finalize path includes a server-side
gateway inquiry call before writing the journal entry.
**Consequences:** Slightly higher finalize latency; absolute
defence against client-side spoofing.

### ADR-013 — `forceCapturedFinalize` bypass with alert

**Status:** Accepted (V19.x)
**Context:** Edge cases where UPayments reports CAPTURED but our
amount validation would otherwise reject (e.g. amount field
missing in callback).
**Decision:** Honour the gateway's CAPTURED signal but fire a
Discord alert (`captured_payment_not_finalized` /
`finalize_failed`).
**Consequences:** No payment is ever silently lost. Operator
follows up on every alert.

### ADR-014 — Two-step destructive migrations

**Status:** Accepted (V20.0)
**Context:** Single-step `DROP COLUMN` migrations broke production
during release windows where the previous app version still
expected the column.
**Decision:** Destructive migrations are split: release N adds
new + backfills + dual-writes; release N+1 removes old.
**Consequences:** Multi-week migration cycles for destructive
changes; zero rollback-window data loss risk.

### ADR-015 — V20.8 frontend domain charter

**Status:** Accepted (V20.8 Phase 2)
**Context:** Per-feature folders had grown organically without a
clear ownership map.
**Decision:** Domain charter at
`web/src/modules/DOMAIN_OWNERSHIP.md`. Barrel-only imports between
modules. No new code in `web/src/pages/` (legacy).
**Consequences:** Clear ownership; linter-enforced barrel
boundaries; legacy `pages/` migrates opportunistically.

## 15. Glossary

| Term | Meaning |
| --- | --- |
| AR | Accounts Receivable. |
| Append-only | INSERT-only at DB; UPDATE/DELETE blocked by trigger. |
| Canonical writer | The single service allowed to write a given table (e.g. `DoubleEntryJournalService` → `JournalEntry`). |
| Decimal | `Prisma.Decimal` — exact 4dp precision. |
| Drift | Divergence between canonical truth and projection (visible via reconciliation). |
| Idempotent | Same call twice → same effect. |
| Journal | Double-entry general ledger (`JournalEntry` + `JournalLine`). |
| KWD / KD | Kuwaiti Dinar (3 decimal places by convention). |
| Outbox | Append-only event log (`FinancialEventOutbox`). |
| Period-lock | Refusal to write journal entries in CLOSED periods. |
| PITR | Point-in-Time Recovery (Postgres WAL replay). |
| RPO | Recovery Point Objective (max data loss in a recovery). |
| RTO | Recovery Time Objective (max time to recover). |
| Reversal | A balanced journal entry that nets the original to zero. |
| Settlement | The act of moving money between AR / wallet / liability accounts on order completion. |
| `sourceRef` | Deterministic unique key on every journal entry; the deduplication primitive. |
| SSoT | Single Source of Truth. |
| trial balance | The identity Σ DR == Σ CR over the entire journal. |
