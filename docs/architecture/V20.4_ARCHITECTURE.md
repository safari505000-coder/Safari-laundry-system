# V20.4 — Enterprise Scalability + Financial Read Architecture

This document is the architectural decision record for V20.4.
It complements the per-phase comments inside the source code,
and explicitly tracks the phases that **require infrastructure
work outside the application repository** (queue isolation,
observability stack, OpenSearch, read replicas, table
partitioning).

The application code in V20.4 is intentionally **additive**.
Nothing in V20.3.x (true accounting, partial payment
correctness, V20.2 wallet-liability account, journal lockstep,
append-only triggers) is changed by V20.4 — see Phase 18 of
the V20.4 brief.

## Phase 1 — Financial Snapshot Layer  ✅ Shipped

- `prisma/migrations/20260508120000_v20_4_financial_snapshot/`
- `src/finance/snapshots/financial-snapshot.types.ts`
- `src/finance/snapshots/financial-snapshot.repository.ts`
- `src/finance/snapshots/financial-snapshot.service.ts`
- `src/finance/snapshots/financial-snapshot.cron.ts`
- `src/finance/snapshots/financial-snapshot.spec.ts`

The `FinancialSnapshot` table is a **derived, rebuildable
projection** of the financial primaries. Dropping the table
and running `FinancialSnapshotService.rebuildAll()` yields
identical numbers — that is the rebuild guarantee. Cron
reconciles every 5 minutes; domain events fan-out into
`refreshOneInBackground` for sub-second propagation after a
write.

## Phase 6 — Queue Isolation  ⏳ Infrastructure decision record

The application uses the existing dispatch in-process bus
(`@nestjs/event-emitter`) for V20.4 fan-out. Multi-process
queue isolation requires Redis + BullMQ (or equivalent) and
operator-controlled queue topologies.

Recommended queue names (reserved here so the codebase has a
single answer the day Redis lands):

| Queue | Producers | Consumers | SLA |
| --- | --- | --- | --- |
| `financial-critical` | settlements, invoice issuance, payments | snapshot projector, journal lockstep | < 1s |
| `notifications` | WhatsApp, SMS, email | `customer-notifications` | best-effort |
| `analytics` | KPI cron, dashboards | `finance-kpi-read-model`, exports | < 5m |
| `audit` | drift inspector, invariant checks | `audit-logs`, Discord alerts | best-effort |
| `reporting` | end-of-day rollups | `accounting`, `payroll` | nightly |
| `ai` | risk scoring, intelligence | `collections-intelligence` | < 60s |
| `exports` | CSV / Excel generation | `exports` module | best-effort |

Hard rule from the V20.4 brief:
- `financial-critical` is **isolated** — it shares neither
  worker pool nor Redis instance with `notifications`,
  `analytics`, `audit`.
- WhatsApp / SMS failures **MUST NEVER** affect settlement
  ACID guarantees.
- Audit scans **MUST NEVER** block POS hot path.

The current `EventEmitter2` listeners (`FinancialSnapshotListener`)
are designed to be portable: each handler does an idempotent
projection refresh by `customerId`. Migrating to BullMQ
becomes a 1-file change (replace `@OnEvent` with a queue
subscriber) per handler.

## Phase 7 — Observability Stack  ⏳ Infrastructure decision record

The application already exposes:
- `MetricsService` (counters, histograms; see
  `src/observability/metrics.service.ts`).
- Structured logs via Nest's `Logger` with consistent
  `[TAG]` prefixes (`[FINANCIAL_DOMAIN_EVENT]`,
  `[FINANCIAL_SNAPSHOT_REFRESH]`,
  `[UI_CONSISTENCY_MISMATCH]`, …).
- Request id middleware (`requestIdMiddleware`).
- Correlation id propagation through `requestContextMiddleware`
  (AsyncLocalStorage).

V20.4 deliberately does NOT bundle the OTel SDK / Sentry SDK
into the production image because the operator chooses the
collector endpoint and the sampling strategy. The integration
points are:

| Tool | Module / Adapter | Status |
| --- | --- | --- |
| Prometheus | `MetricsService` exposes `/metrics` | live |
| Grafana | dashboards-as-code in `ops/grafana/` | not in scope |
| Loki | structured stdout logs are scrape-ready | live |
| OpenTelemetry | `@opentelemetry/sdk-node` opt-in via env | not yet wired |
| Sentry | DSN via `SENTRY_DSN` env, init in `main.ts` | not yet wired |

The `[FINANCIAL_DOMAIN_EVENT]` log tag in the typed publisher
is the trace anchor — every event carries `customerId` and
`correlationId`, so a Loki query ties the snapshot refresh
back to the originating financial write.

Recommended metrics (operator-side dashboards):
- settlement_latency_ms (histogram)
- transaction_rollback_total (counter)
- invariant_violation_total (counter)
- queue_delay_ms (histogram)
- journal_drift_total (counter)
- lock_contention_total (counter)
- db_query_latency_ms (histogram, by query name)
- payment_throughput (counter)

Most of these already have backing log lines in V20.1-v4 / V20.2.

## Phase 9 — Collections Intelligence  ✅ Shipped

- `src/finance/collections-intelligence/collections-intelligence.service.ts`
- `src/finance/collections-intelligence/collections-intelligence.module.ts`
- `src/finance/collections-intelligence/collections-intelligence.spec.ts`

Deterministic, explainable scoring (`riskScore`,
`paymentProbability`, `agingSeverity`, `priority`,
`behaviorScore`). Inputs (`overdueDays`, `missedPromises`,
`partialPaymentFrequency`, `reminderIgnores`, invoice size,
historical payment speed) are computed from primaries; the
weighting constants live next to the scorer so the
Accountant can audit the formula. The `inputDigest`
(FNV-1a) makes "same inputs → same score" trivially
verifiable in incident triage.

`missedPromises` and `reminderIgnores` return 0 today; they
slot in once the WhatsApp tracking + promise-to-pay tables
ship.

## Phase 10 — Search Engine  ⏳ Infrastructure decision record

OpenSearch / Elasticsearch is operator-deployed. Once the
cluster is reachable, the service-side hooks land in three
files (each ≤ 200 lines):

- `src/search/opensearch.service.ts` — typed wrapper around
  the official `@opensearch-project/opensearch` client.
- `src/search/financial-indexer.listener.ts` — subscribes to
  the same `finance.*` events the snapshot listener consumes
  and writes documents to the relevant index
  (`customers-v1`, `invoices-v1`, `collections-v1`,
  `audit-logs-v1`, `financial-timeline-v1`).
- `src/search/search.controller.ts` — read-only routes
  (`/api/search/customers`, `/api/search/invoices`).

Indexes are append-only; reindex from primaries via the same
projector pattern as `FinancialSnapshotService.rebuildAll()`.

## Phase 13 — Read Replica Support  ⏳ Infrastructure decision record

Postgres read-replica readiness is two changes when the
operator provisions a replica:

1. Add a second Prisma datasource (`replica`) in
   `prisma/schema.prisma` and a corresponding `PrismaReadOnlyService`
   that wraps the replica client.
2. Switch the read-side surfaces to consume the read-only
   service:
   - `DebtVisibilityService` (snapshot reads)
   - `FinanceKpiReadModel` (KPI snapshot reads)
   - `FinancialTimelineService`
   - `CollectionsIntelligenceService`
   - all read-models under `src/read-models/`

Write surfaces (`CustomerLedgerService`, `JournalSourceService`,
the V20.3 invariants, the V20.2 wallet-liability journal
writes) stay on the primary.

The split is intentionally a flag-gated change because the
replica lag must be < 1s for the snapshot reads to feel
real-time; operators who have higher lag should keep reads on
the primary.

## Phase 14 — Table Partitioning  ⏳ Infrastructure decision record

Monthly partitions are a Postgres DDL change owned by the
DBA. The migration template (commit when partitions land):

```sql
-- prisma/migrations/<timestamp>_v20_4_partition_journal_line/migration.sql
-- Convert "JournalLine" into a partitioned table by createdAt.
-- See: https://www.postgresql.org/docs/current/ddl-partitioning.html
ALTER TABLE "JournalLine" RENAME TO "JournalLine_legacy";
CREATE TABLE "JournalLine" (
  LIKE "JournalLine_legacy" INCLUDING ALL
) PARTITION BY RANGE ((SELECT "createdAt" FROM "JournalEntry"
                       WHERE "JournalEntry"."id" = "entryId"));
-- Partition windows pre-created via cron `pg_cron` job:
--   CREATE TABLE "JournalLine_2026_05" PARTITION OF "JournalLine"
--     FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');
INSERT INTO "JournalLine" SELECT * FROM "JournalLine_legacy";
DROP TABLE "JournalLine_legacy";
```

Apply the same shape to `JournalEntry`, `DebtLedgerEntry`,
`TransactionHistory`. Each partition migration is a separate
PR with read-write smoke tests + rollback DDL.

Slow-query logging is operator-side (Postgres
`log_min_duration_statement`). The `OBSERVABILITY_DB_LATENCY_MS`
env in `MetricsService` prints any query above the threshold
to the structured log so the operator can spot regressions
without enabling Postgres-side slow logs.

## Phase 18 — Financial Safety Preservation  ✅ Verified

V20.4 is **additive-only**. The following V20.1-v4 / V20.2 /
V20.3 / V20.3.1 / V20.3.2 invariants are unchanged:

- Phase 18 invariants (V20.1-v4 wallet vs ledger lockstep)
- Phase 29 journal lockstep (`LEDGER_JOURNAL_DIVERGENCE`)
- Append-only ledgers + immutable journal triggers
- V20.3 true-accounting flow (`V20_3_TRUE_ACCOUNTING=true`)
- Deterministic `sourceRef`s
- Idempotency guarantees on debt-mutating writes
- Backfill audit lock (V20.1-v4 Phase 21)
- Drift inspector + `assertUiConsistency` (V20.3.2)

## Phase 19 — Success Criteria  ✅ Met

- Operational screens (Subscribers, Outstanding, Customer 360,
  Dashboards) read snapshots — no live ledger aggregation.
- `DebtVisibilityService` is the single canonical source.
- UI consistency assertions wired into write paths
  (V20.3.2 inheritance) — every debt-mutating commit logs
  `[UI_CONSISTENCY_*]`.
- Financial writes remain ACID-safe (no V20.4 changes).
- Dashboards never scan ledgers live (`FinancialKpiSnapshot`).
- Queue failures never affect settlements (event listeners
  are fire-and-forget; absorber in publisher).
- Bank-grade auditability preserved (Phase 18).
- The architecture leaves room for read replicas, table
  partitioning, OpenSearch, and queue isolation as
  operator-driven follow-ups.
